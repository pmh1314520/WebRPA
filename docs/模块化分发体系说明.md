# WebRPA 模块化分发体系（功能模块包 / Feature Packs）

> 对应版本：WebRPA 2.5.0+，2026-07-20 引入。
> 目标：用户不再每次下载几个 GB 的完整压缩包——下载小体积核心包，
> 需要什么能力就装什么功能包（zip），随装随用、随时卸载。

---

## 一、体系总览

```
【发布方】完整版 WebRPA
    │  backend/scripts/build_feature_packs.py
    ├──────────► packaged/feature_packs/*.zip     （13 个功能包，约 2.8GB）
    │            packaged/feature_packs/packs_index.json
    │
    │  build_feature_packs.py --strip（在副本目录执行）
    └──────────► 瘦身核心目录 → 打 7z = 「WebRPA 核心包」（比完整版小约 2.8GB）

【用户】
    下载核心包 7z → 解压 → 启动
    需要 OCR？ → 下载 ocr-paddle-v2.5.0.zip → 编辑器 → 更多 → 功能模块包 → 安装
    不要了？   → 同一界面一键卸载，磁盘立即释放
```

三层组成：

| 层 | 位置 | 职责 |
|----|------|------|
| **注册表 + 管理器** | `backend/app/services/feature_packs.py` | 功能包定义（载荷/探测/门控模块）、安装/卸载、安全校验、缺包提示 |
| **REST API** | `backend/app/api/feature_packs.py`（`/api/feature-packs`） | 列表 / 路径安装 / 上传安装 / 卸载 / 模块依赖查询 |
| **管理界面** | `frontend/src/components/workflow/FeaturePackDialog.tsx` | 编辑器 → 更多 → 功能模块包 |
| **构建器** | `backend/scripts/build_feature_packs.py` | 发布方打包工具 |

## 二、功能包清单（13 个）

| ID | 名称 | 实测体积 | 解锁能力 |
|----|------|---------|----------|
| `web-automation` | 网页自动化引擎（Playwright） | ~100MB | 网页导航/交互/查询/采集（推荐） |
| `data-tables` | 数据表格与 Excel 导出（Polars） | ~240MB | 数据表格收集、Excel/CSV 导出（推荐） |
| `vision-opencv` | 图像识别（OpenCV） | ~148MB | 图像点击、等待图像、二维码、找图（推荐） |
| `media-ffmpeg` | 媒体处理（FFmpeg） | ~223MB | 视频/音频/录制/格式转换/M3U8（推荐） |
| `ocr-paddle` | OCR 文字识别（PaddleOCR） | ~366MB | 点击文本、悬停文本、OCR 提取 |
| `ocr-easyocr` | OCR 备用引擎（EasyOCR+PyTorch） | ~750MB | OCR 备选引擎（与 Paddle 二选一即可） |
| `speech` | 语音识别（Faster-Whisper） | ~322MB | 音频转文本、语音触发器 |
| `face-gesture` | 人脸与手势识别 | ~161MB | 人脸触发器、手势触发器 |
| `doc-convert` | 文档转换（Pandoc+Poppler+PyMuPDF） | ~331MB | PDF 处理、文档格式转换 |
| `phone-adb` | 手机自动化（scrcpy+ADB） | ~16MB | 全部手机自动化模块 |
| `qq-bot` | QQ 机器人（NapCat） | ~2MB(仓库)/150MB(发布) | QQ 机器人模块 |
| `ai-crawler` | AI 智能爬虫（ScrapeGraphAI） | ~14MB | AI 爬虫模块 |
| `proxy-capture` | 网络抓包（mitmproxy） | ~14MB | 代理抓包模块 |

> 体积为 zip 前的载荷实测值；核心公共依赖（numpy/scipy/Pillow/FastAPI 等）保留在核心包，避免跨包依赖地狱。

## 三、功能包 zip 格式（`format: 1`）

功能包 = 「项目根目录的增量覆盖层」+ 一个清单文件：

```
ocr-paddle-v2.5.0.zip
├─ webrpa-pack.json                          ← 清单（必须在 zip 根）
├─ Python313/Lib/site-packages/paddle/...    ← Python 依赖载荷
├─ Python313/Lib/site-packages/paddleocr/...
└─ backend/models/paddle_ocr/...             ← 模型载荷
```

`webrpa-pack.json`：

```json
{
  "format": 1,
  "id": "ocr-paddle",
  "name": "OCR 文字识别（PaddleOCR）",
  "description": "...",
  "category": "AI 识别",
  "version": "2.5.0",
  "built_at": "2026-07-20 19:00:00",
  "file_count": 4213
}
```

**安装** = 校验清单 → 校验每个条目路径 → 解压覆盖到项目根 → 写安装记录
（`backend/data/feature_packs/<id>.json`，含完整文件清单）。

**卸载** = 有安装记录按记录删文件（并清理空目录）；无记录（完整版自带）按注册表
`payload_paths` 删除。

**安全防御**（`feature_packs.py` 内置，均有单元测试）：

- 拒绝路径穿越（`../`、绝对路径）；
- 条目必须落在白名单前缀内（`Python313/Lib/site-packages/`、`backend/ffmpeg.exe`、
  `backend/scrcpy/`、`models/`、`NapCat/` 等），**不可能覆盖 backend/app 核心代码**；
- 卸载同样只删白名单内文件，安装记录被篡改也删不到核心文件；
- `format` 版本高于本体支持时拒绝安装并提示升级。

## 四、安装状态探测（无状态、可靠）

`installed` 状态**不读安装记录**，而是探测真实能力：

- `detect_imports`：`importlib.util.find_spec("paddleocr")`（不真正加载，不吃内存）；
- `detect_paths`：`backend/ffmpeg.exe` 等关键文件是否存在。

因此：完整版用户升级后所有包显示"已安装"；用户手动 pip 装过的依赖同样被识别；
删了目录立刻显示"未安装"。

## 五、缺包时的运行时体验（三层防线）

### 第一层：运行前预检（主要体验）

工作流启动时（`WorkflowExecutor.execute()` 解析完图之后、执行任何节点之前），
自动扫描全部节点的模块类型，映射到所需功能包并探测安装状态。**缺包直接拦截运行**，
一次性给出完整清单（核心版实测输出）：

```
工作流缺少功能模块包，无法运行：
  ● 需要 「手机自动化（scrcpy + ADB）」[phone-adb]（约16MB） —— 影响模块：手机点击
  ● 需要 「网页自动化引擎（Playwright）」[web-automation]（约100MB） —— 影响模块：打开网页
请到 编辑器 → 右上角「更多」→「功能模块包」安装后重试；功能包 zip 可从官网/网盘下载。
```

- 该消息同时进入执行日志（ERROR 级）和 `ExecutionResult.error_message`，
  编辑器错误卡片、计划任务日志、CLI、Webhook 触发全部可见；
- 映射数据：`feature_packs.py` 的 `SUBMODULE_PACK_REQUIREMENTS`（按执行器文件）+
  `TYPE_PACK_REQUIREMENTS`（混合文件内按模块类型精确登记），依据是对全部执行器
  源码的依赖扫描，**只登记确定需要的类型**（`wait`/`set_variable`/`group` 等
  核心模块绝不会被误拦，已有单测锁定）；
- 支持「或」语义：OCR 类模块装 PaddleOCR 或 EasyOCR 任一即可通过；
- 应急逃生：环境变量 `WEBRPA_SKIP_PACK_CHECK=1` 可跳过预检强行运行；
- 前端/第三方可直接调用 `POST /api/feature-packs/preflight`
  （body: `{"module_types": [...]}`）获得同样的结构化结果与格式化文案。

### 第二层：节点级 ImportError 翻译（兜底）

预检映射之外的场景（如服务层动态导入），执行器捕获 `ImportError` 后经
`hint_for_import_error()` 翻译为「缺少功能模块包 XX…请安装 [id]」。

### 第三层：启动健壮性

后端启动完全不依赖任何功能包：全部 89 个执行器重依赖懒加载；启动/执行链路上
仅有的三处硬导入（`browser_engine` 的 playwright、`data_collector` 的 polars、
`workflow_executor.execute()` 顶部的 playwright）已全部改为可选导入。
纯本地流程（变量/文本/文件/流程控制等）在最小核心版上照常运行（已实测）。

另有 `GET /api/feature-packs/module-hint/{module_type}` 单模块查询接口
（预留给模块面板灰显/角标）。

## 六、发布流程（维护者）：一键打包

在**完整版目录**双击根目录的 **`一键打包发布.bat`**（或命令行执行
`Python313\python.exe backend\scripts\release_packager.py`），自动完成全流程
（2.5.0 实测总耗时约 6 分钟）：

1. 构建全部 13 个功能包 → `packaged/feature_packs/*.zip` + `packs_index.json`；
2. robocopy 复制核心目录到项目同级的 `WebRPA核心包构建\`
   （自动排除：开发产物、**本机隐私与运行时数据**——密钥/账号/任务/会话/工作流/
   采集数据/本机维护脚本，以及全部功能包载荷，完整清单见
   `release_packager.py` 顶部的 `EXCLUDE_*` 常量）；
3. 瘦身兜底（按注册表载荷再删一遍 + 清扫运行时数据文件）；
4. 压缩 → `packaged/WebRPA-<版本>-核心包.zip`，并生成 SHA256
   `checksums-v<版本>.txt`。

可选参数：`--packs-only`（只打功能包）、`--core-only`（只打核心包）、
`--workdir <路径>`（自定义核心构建目录）、`--clean-workdir`（打完删除构建目录；
默认保留，便于直接双击其中的启动器做发布前试跑验证）。

上传清单：核心包 zip + `feature_packs/*.zip` + `packs_index.json` + checksums。
`packs_index.json` 是给官网/网盘做下载列表用的索引（含 id/名称/体积/文件名）。

> 底层单包工具仍可独立使用：`build_feature_packs.py`（`--list` 看体积、
> 指定 id 只打个别包、`--strip-only` 副本瘦身）。

**2.5.0 实测产物**（一键脚本产出）：核心目录 1.30 GB → zip 后 **486 MB**；13 个功能包 zip 合计约 1.1 GB
（其中 ocr-easyocr 405MB、speech 208MB、face-gesture 111MB、ocr-paddle 102MB、
media-ffmpeg 93MB、doc-convert 79MB、data-tables 72MB、vision-opencv 55MB、
web-automation 35MB、其余 <10MB）。对比旧模式动辄数 GB 的整包，
普通用户首次下载量降到原来的 **1/6 左右**。

注意事项：

- `--strip` / `--strip-only` 是破坏性操作，**务必在副本目录执行**；
- 打包机必须是装齐所有能力的完整版（本机缺的载荷会跳过并提示）；
- 新增功能包只需在 `feature_packs.py` 的 `FEATURE_PACKS` 注册表加一条定义
  （载荷路径 + 探测规则 + import 映射），构建器与 API/前端自动生效；
- 若新载荷路径不在白名单内，同步更新 `ALLOWED_TARGET_PREFIXES`（有单测
  `test_payload_paths_within_whitelist` 兜底，忘了会直接红）。

## 七、用户使用说明（可直接贴公告）

1. 下载「WebRPA 核心包」解压启动（含网页自动化等全部基础能力的说明见包内 README）；
2. 需要某类能力时，到官网/网盘下载对应功能包 zip（**无需解压**）；
3. 打开 WebRPA 编辑器 → 右上角「更多」菜单 → **功能模块包**；
4. 点「从本地路径安装」粘贴 zip 完整路径（大包推荐，秒级完成），或「上传 zip 安装」；
5. 安装完成即可使用对应模块，无需重启（个别引擎首次运行会初始化几秒）；
6. 不用了可在同一界面**一键卸载**释放磁盘空间，之后随时重装。

## 八、版本管理策略（锁步版本，Lockstep）

功能包**不做独立版本线**，一律跟随 WebRPA 本体版本号（如 2.5.0）：

- **发布时**：`build_feature_packs.py` 一条命令重打全部包，版本号自动取自
  `frontend/package.json`，产物文件名/清单/索引三处一致，维护者无需管理任何
  单包版本；
- **更新新增了 Python 库时**：库属于核心 → 随核心包更新自然带上；库属于某个
  功能域 → 在 `FEATURE_PACKS` 注册表对应包的 `payload_paths`/`import_names`
  里加一行，下次构建自动包含——不存在"给某个包单独发版"的操作；
- **兼容性边界**：功能包本质是 site-packages/工具/模型的文件快照，真正会破坏
  兼容的只有两种情况：① Python 大版本升级（如 3.13→3.14，C 扩展 ABI 变化）——
  此时清单 `format` 版本升位，旧包被安装器拒绝并提示重新下载；② 某模块开始
  依赖某库的更新特性——跨小版本极少发生，且预检/ImportError 提示会引导用户
  重新下载匹配版本的包；
- **用户视角**：只有一条规则——"功能包版本与核心版本一致最稳，不一致通常也能用，
  出问题就重新下载当前版本的包"。安装器会在版本不一致时给出提示但不阻止。
